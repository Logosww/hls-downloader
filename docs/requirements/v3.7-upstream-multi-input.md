# hls-transmux 双路合流需求

状态：上游已发布 v0.5.0，库接入与验收已实现，待 v3.7 发布。更新日期：2026-10-04。

本文面向 hls-transmux 与 hls-downloader 维护者，定义 hls-downloader v3.7 音轨选择所依赖的上游能力、职责边界与发布验收标准。需求基线为 hls-downloader v3.6.0 与 hls-transmux 0.4.2；当前库已升级至 hls-transmux 0.5.0。下文保留上游需求及其原始缺口，用于追溯。

## 交付目标

已确认首期在 Browser 与 Node 同步交付单音轨合流与 WebVTT 字幕独立导出；音轨合流必须覆盖 download、writable、stream 三条路径，不能仅交付完整文件下载。

运行时范围已确认：Browser 与 Node 均覆盖 download、downloadToWritable、downloadToStream。Node 新增 WHATWG WritableStream 输出，复用 core 的异步背压与 close/abort 契约。

调用者未指定音轨时由库自动选择默认音轨；显式选择不存在的轨道必须失败，不得静默回退。字幕独立导出，不内嵌 MP4。

首期建议沿用现有编码与协议边界：普通 VOD、TS/fMP4、MAP/BYTERANGE，视频 AVC/HEVC、音频 AAC-LC。多音轨容器、Packed Audio、新增 codec、加密、Live、discontinuity、转码组合、aria2 组合和双路 resume 不纳入本次上游交付；原有单路能力不得退化。

## v0.4.2 基线与缺口

当前上游已经提供 MP4 bytes、文件输出、非 seekable fMP4 AsyncWrite、CancelToken、可取消写入，以及关闭末尾 mfra 索引的选项。应复用这些设施。

当前输入解析与增量处理围绕单个 media playlist 展开：逐段解封装，从首批媒体确定轨道与归零原点，并按该列表生成进度及恢复状态。alternate media groups 被拒绝，尚无独立音频输入的联合调度契约。

Browser 的 WASM 桥接属于 hls-downloader 仓库。现有 DemandSource 只接收一个 playlist；DemandWriter 已等待 JS 写入 Promise。桥接扩展由本库负责，不能用它替代上游时间轴和双路 mux 支持。

## 上游功能要求

### 双路输入与轨道选择

- 接受已解析选择的主媒体输入与可选外置音频输入；每路有独立资源位置，并能通过自定义 Source 读取 playlist、初始化段与媒体分片。
- 保留重定向后的相对 URI 解析、MAP、显式与隐式 BYTERANGE 语义；同一 URL 的不同范围不能混用缓存。
- 主媒体可能已含音频。指定外置音频后，只保留主媒体视频和外置音频，不能同时输出两条音轨。
- 没有外置输入时保留单路行为；库将无 URI 的音频 rendition 解析为使用主媒体内嵌音频。
- 上游无需实现语言偏好、DEFAULT/AUTOSELECT 或 master 的业务选轨策略。输入中不得依赖用户语言或库的私有配置。

### 共同时间轴

- 对两路 PTS/DTS 使用共同输出原点，保留原始相对偏移，不得分别归零，也不得按分片序号拼对。
- 支持不同 timescale、不同分片数量和边界、非零起点、音频先于或晚于视频，以及 TS 33 位时间戳回绕。
- 在各自的解码顺序中维持合法 DTS，保留合法 PTS 重排；跨分片的末样本时长延续现有时间戳校验要求。
- 一路正常结束后继续处理另一条，不自动截短或补静音。时间戳重置、非法重叠、配置变化或无法建立可靠映射时明确失败，不猜测同步偏移。
- bytes、文件及 fMP4 writer 三条路径对同一输入采用一致的时间轴转换。

### 初始化与增量调度

- 写出 fMP4 初始化段前确定所需两条轨道及 codec 配置，保证首个 moov 已完整声明输出轨道。
- 初始化只能进行必要的有界探测，不得要求下载完整输入；探测读取的资源和样本应供后续处理复用。
- 按时间轴推进两路媒体，允许两路不同的分片边界；不能假设每一个输出 fragment 都有两条轨道的样本。
- 不支持的输入在能够判定时立即失败。初始化后才暴露的问题可以使流失败，但必须停止后续处理，不能以成功结果掩盖不完整内容。

### 输出与背压

- 同一双路输入覆盖 MP4 bytes、文件输出与 FragmentedMp4 AsyncWrite。文件 finalize 不能改变已确定的音画偏移。
- writer 无需 seek；支持短写和 Pending，等待写入完成后才能推进相应输出状态。写失败停止输入调度。
- 明确两路预取、解封装样本和待写 fragment 的缓冲边界；writer 持续阻塞时，不得持续读取完整媒体或积累无界队列。
- 有界内存指增量路径的媒体缓冲不随总时长增长，可受并发预算、单段大小和有界 lookahead 影响。MP4 bytes 的最终结果缓冲、完整 playlist 元数据应单独说明，不得宣称所有路径恒定内存。
- write_mfra 为 false 时不得累计全程随机访问索引；为 true 时说明索引随 fragment 数增长的代价。

### 取消与错误

- 一个 operation 的取消覆盖两路 manifest、初始化与分片读取、调度等待、输出写入和文件 finalize。
- 任一路失败后停止另一条的后续请求，并释放内部持有的 future、样本和输出状态；不得留下脱离 operation 生命周期的后台生产任务。
- 返回取消或失败后，不再调用输出和进度回调。对于自定义 Source，明确要求其异步任务被丢弃后不得继续产生可见副作用；JS fetch 的实际中止由库的 AbortSignal 桥接完成。
- 保留现有错误类别，并提供机器可读的输入角色和分片上下文，供库映射稳定错误。不得要求库通过解析英文错误字符串判断来自主媒体还是音频。
- 已写出的流式字节无法回滚；上游报告失败，库负责终止消费端及清理其拥有的资源，不发布成功结果。

### 进度与时间轴报告

- 进度能够区分主媒体与音频输入，包含该路分片索引及两路聚合计数；媒体分片总数不包含初始化段，预取不等于已完成处理。
- 新双路进度不得强制携带旧单路 resume checkpoint，也不得生成可被误认为可恢复的伪 checkpoint。双路与 resume 组合应在修改输出前拒绝。
- 暴露原始媒体时间到输出时间的精确映射，包含时间单位、原点和回绕解释所需信息；优先使用整数及 timescale，避免仅返回浮点秒数。
- 时间轴映射在准备阶段完成后、正式媒体输出前可取得，并在最终报告中保持一致，供独立 WebVTT 导出使用。无需为了获取映射而先完成视频下载。

## 建议接口结构

以下是能力结构，不是已确定的 Rust 函数或类型命名。上游可以采用其他兼容设计，但必须满足上述可观察契约。

```text
准备阶段
  主媒体输入 + 可选已选音频输入 + 取消及资源预算
    → prepared session
    → 两条轨道配置 + 共同时间轴映射

执行阶段
  prepared session → MP4 bytes
                   → 文件及必要的 finalize
                   → 非 seekable fMP4 AsyncWrite
```

prepared session 应拥有探测过程中读取的资源和样本，使执行阶段可以直接继续；放弃该 session 时释放资源。准备和执行均应可取消。旧单路公开入口保持可用，新增 API 的具体兼容方式由上游评审确定。

## 库的职责

| 事项           | hls-downloader 负责的工作                                                               |
| -------------- | --------------------------------------------------------------------------------------- |
| 轨道发现与选择 | 补齐 Browser/Rust/N-API 元数据，按 variant 关联组选择默认或指定音轨，检测不存在的轨道   |
| 请求策略       | 保持 headers、Browser browserRequest、重试、总并发预算和 operation 级取消的一致性       |
| Browser WASM   | 支持两路 playlist 与资源读取，等待 JS writable Promise，处理取消及回调注册释放          |
| Browser stream | 从全量预加载改为增量读取；保留现有同步 onChunk 契约，不承诺等待异步消费者返回的 Promise |
| Node stream    | 保证分块回调交付完成后再完成 operation，并验证桥接队列不会无限积累                      |
| 输出生命周期   | writable 的 close/abort、Blob URL 管理、文件发布和失败清理，以及 operation 事件隔离     |
| 字幕导出       | WebVTT 解析、MAP、时间映射、回绕、cue 去重与序列化；使用上游提供的共同时间轴            |
| 公共契约       | 类型、capabilities、稳定错误、使用限制、中英文文档及发布入口验证                        |

字幕协议规则以 [RFC 8216 第 3.5 节](https://www.rfc-editor.org/rfc/rfc8216.html#section-3.5) 为依据。字幕解析与字幕 mux 不属于本次上游实现需求。

## 上游验收矩阵

所有协议用例使用可重复的本地 fixture。成功标准包含输出内容与生命周期，不以 API 返回成功作为唯一证据。

| 场景                                            | 必须验证的结果                                                                   |
| ----------------------------------------------- | -------------------------------------------------------------------------------- |
| TS 与 fMP4 双路输入                             | bytes、文件、writer 都输出指定音轨；ffprobe 验证轨道、codec、duration 与时间戳   |
| 主媒体自带音频                                  | 选择外置音频后仅输出所选音频，使用可辨识音频 fixture 验证内容                    |
| 分片数量和边界不一致                            | 无丢样本、重复样本或按序号造成的错位                                             |
| 非零起点、正负相对偏移、不同 timescale、TS 回绕 | 保留 fixture 的已知相对偏移；偏差不超过相应样本时长，并记录量化方式              |
| 一条轨道先结束                                  | 正常保留另一条的剩余样本，不擅自截短或补静音                                     |
| MAP 与 BYTERANGE                                | 两路范围与初始化资源均正确，包括同 URL 不同范围                                  |
| 慢 writer、短写、Pending                        | 输出正确，阻塞期间读取受控，媒体缓冲不随总时长增长                               |
| 写失败、任一路读失败、请求挂起时取消            | 及时终止，无死锁、无迟到回调、无继续推进的另一条输入                             |
| 流式首段                                        | 全部下载结束前可解析初始化信息与两条轨道，后续片段可持续解析                     |
| 时间轴报告                                      | 准备阶段与最终报告映射一致，可用于已知 WebVTT cue 与视频的对齐                   |
| 非法输入与配置变化                              | 返回确定错误及输入上下文，不输出成功结果                                         |
| 原有单路与 resume                               | 既有契约测试通过；双路 resume 明确拒绝且不修改已有输出                           |
| native 与 WASM                                  | 相同 fixture 在两种目标中满足一致轨道与时间轴契约，无 native 专属依赖泄漏到 WASM |

增量测试应分别测量有无 mfra 索引；通过受控 Source 与 writer 记录请求数、在途任务、待写数据量和取消后调用情况，不能只比较进程总内存。

## 交付顺序与评审事项

1. 上游确认双路输入、时间轴映射、错误与进度接口，以及明确的缓冲预算。
2. 先完成双路 fMP4 writer 与直接契约测试，优先验证调度、背压和取消。
3. 接通 MP4 bytes 与文件 finalize，验证三种输出的一致性及旧单路回归。
4. native/WASM 验收通过后发布正式上游版本，库同步升级；不使用 vendor patch 代替正式接口。
5. 库完成三条路径接入、字幕导出和端到端测试后，再发布 v3.7。

v0.5.0 已确定 `HlsInputs`、`prepare_hls`、`PreparedTransmux`、`TimelineMapping`、`SessionError` 及 `ResourceBudget`。库采用默认每路两段探测上限，总读取预算取有效 downloadConcurrency；流式输出关闭 mfra。JS 传输的 i128 使用十进制字符串，字幕计算使用 BigInt。

为保留单路允许的时间轴间隙，未选择外置音频的既有输出继续使用旧单路 mux API（依赖版本仍为 0.5.0）。双路与字幕探测使用 prepared API。Node 使用 operation 独有临时目录处理上游文件发布和 partial 清理。

验收入口：`test:unit`、`test:native:contract`、`test:native:prepared`、`test:native:resume`、`test:browser:renditions`、`test:types:renditions`、`test:publish`。跨平台 native CI 和正式发布仍由发布流水线完成。
